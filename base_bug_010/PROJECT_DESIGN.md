# 结构化日志告警聚合器项目设计文档

## 1. 项目概述

### 1.1 项目名称

结构化日志告警聚合器（Structured Alert Aggregator）

### 1.2 项目定位

本项目是一个使用 Go 开发的后端告警聚合服务，用于接收来自应用服务、基础设施和中间件的结构化错误日志，对相似错误进行归并，控制重复通知，并持续追踪告警的确认、恢复和关闭状态。

系统面向多服务、多环境的生产场景设计，不是简单的日志接收 Demo。项目采用分层架构，包含 HTTP API、领域处理、持久化、数据库迁移、后台归并任务、通知控制、指标监控和自动化测试等完整模块。

### 1.3 解决的问题

在微服务系统中，同一个根因可能在短时间内产生数千条重复日志。如果每条日志都触发独立通知，会造成通知风暴，增加值班人员负担，也会掩盖真正重要的问题。本系统通过稳定指纹、消息归一化和相似度策略，把同类错误收敛成一个告警组，并以计数、时间线和样本事件的方式保留上下文。

## 2. 业务目标

1. 接收统一格式的结构化日志事件。
2. 将服务、环境、日志级别和归一化后的错误消息组合成稳定指纹。
3. 合并短时间内重复或高度相似的错误。
4. 首次发生时发送通知，窗口内抑制重复通知。
5. 对持续发生的告警按退避策略再次提醒。
6. 在错误停止后自动判断恢复，也允许人工恢复。
7. 支持人工确认，记录处理人和处理时间。
8. 保留原始事件、告警组和通知历史，便于审计和问题分析。
9. 通过健康检查和指标接口支持运行状态监控。
10. 在服务重启后恢复此前的告警状态和通知状态。

## 3. 功能范围

### 3.1 结构化日志接入

系统通过 `POST /v1/events` 接收 JSON 事件。事件至少包含：

- `service`：服务名称。
- `environment`：运行环境，例如 `prod`、`staging`。
- `level`：日志级别，支持 `debug`、`info`、`warn`、`error`、`fatal`。
- `message`：原始错误消息。

可选字段包括 trace ID、request ID、发生时间和业务标签。服务端会校验字段、限制消息长度、补齐事件 ID 和缺失时间。

### 3.2 消息归一化

为了避免动态值导致同一错误被拆成多个告警，系统会对消息进行归一化：

- 统一大小写和空白字符。
- 将数字、耗时和计数替换为占位符。
- 将 UUID 替换为统一占位符。
- 对 token、password、secret、api key 等敏感值进行脱敏。
- 保留错误文本的结构和关键语义。

例如：

```text
timeout calling db host=db-1 latency=1200ms
timeout calling db host=db-2 latency=900ms
```

会被归一化为相近的消息模板，并进入同一聚合判断流程。

### 3.3 相似错误合并

系统首先使用 SHA-256 生成稳定指纹。指纹输入包括服务、环境、级别、归一化消息和排序后的业务标签。

聚合规则如下：

1. 指纹完全相同，直接归入同一告警组。
2. 指纹不同但服务、环境和级别相同，计算 token Jaccard 相似度。
3. 相似度达到阈值时，视为同一类错误。
4. trace ID、request ID 等请求级字段不参与核心指纹。
5. 不同环境的事件不能合并，避免测试环境影响生产告警。

告警组会记录事件数量、首次发生时间、最近发生时间和若干样本事件 ID。

### 3.4 告警生命周期

告警状态包括：

- `open`：告警正在发生，尚未恢复。
- `acknowledged`：已被值班人员确认，但问题仍可能存在。
- `resolved`：已恢复或被人工关闭。

状态转换：

```text
新事件 -> open
open -> acknowledged
open -> resolved
acknowledged -> resolved
resolved + 新事件 -> open
```

当告警在 `resolve_after` 时间内没有新事件时，后台任务会自动将其标记为恢复。如果恢复后再次收到相同错误，系统会重新打开告警，并保留历史通知记录。

### 3.5 通知控制

通知策略用于避免同一个告警反复发送消息：

- 第一次事件进入告警组时发送 `triggered` 通知。
- 通知窗口内的新事件只增加计数，不重复发送。
- 超过窗口后，根据指数退避时间决定是否发送 `reminder`。
- 告警恢复时发送一次 `resolved` 通知。
- 每条通知记录发送类型、渠道、内容、时间、投递结果和错误信息。

默认退避时间会随着通知次数逐步增加，并设置最大级别，避免持续故障造成高频通知。

### 3.6 后台归并与恢复

后台 Worker 按固定周期执行：

1. 扫描未处理事件。
2. 计算指纹并归并到告警组。
3. 更新告警计数和最近发生时间。
4. 根据通知策略触发通知。
5. 扫描长时间没有新事件的告警并自动恢复。
6. 清理超过保留期限且已经处理的原始事件。

Worker 使用可取消的 context，在服务停止时释放 ticker 并等待 HTTP 服务优雅退出。

## 4. 系统架构

项目采用分层结构：

```text
cmd/aggregator
    启动参数、依赖组装、优雅停机

internal/api
    HTTP 路由、请求解析、响应编码、状态码处理

internal/aggregate
    告警聚合、状态机、自动恢复、人工操作

internal/normalize
internal/fingerprint
internal/similarity
    消息归一化、指纹生成、相似度计算

internal/store
internal/migrate
internal/retention
    数据持久化、数据库迁移、数据保留

internal/notify
internal/policy
    通知投递、通知窗口、退避策略

internal/worker
    后台事件归并和恢复调度

internal/metrics
internal/health
internal/logging
    指标、健康检查、结构化运行日志
```

各层通过明确的结构体和方法协作，API 层不直接修改存储数据，领域层不依赖 HTTP 请求细节，便于后续替换数据库或通知渠道。

## 5. 数据模型

### 5.1 Event

原始日志事件，保存服务、环境、级别、消息、标签、时间和处理状态。

### 5.2 Alert

聚合后的告警组，保存稳定指纹、状态、计数、时间线、通知次数、下次通知时间和样本事件。

### 5.3 Notification

通知审计记录，保存告警 ID、通知类型、渠道、内容、投递时间和投递结果。

### 5.4 Snapshot

持久化快照根对象，包含 schema version、事件列表、告警列表和通知列表。启动时读取快照，并执行幂等迁移。

## 6. 数据库与迁移

当前实现使用 JSON 文件数据库，以降低部署依赖，同时保留数据库抽象边界。写入过程采用以下策略：

1. 对 Store 加写锁。
2. 在内存快照上执行修改。
3. 将完整快照写入临时文件。
4. 通过原子 rename 替换正式文件。
5. 释放锁。

这种方式可以避免服务在写入过程中留下半个 JSON 文件。迁移模块通过 `schema_version` 判断当前结构版本，版本号低于目标版本时补齐新字段，重复启动不会重复修改数据。

后续可以在不改变领域层接口的前提下，将 Store 替换为 SQLite 或 PostgreSQL 实现。

## 7. HTTP API

### 7.1 创建事件

```http
POST /v1/events
Content-Type: application/json
```

响应：

```json
{
  "id": "evt_123",
  "status": "accepted"
}
```

接口返回 `202 Accepted`，表示事件已持久化并等待后台归并。

### 7.2 查询告警

```http
GET /v1/alerts?status=open&service=payments
```

支持按状态和服务过滤，返回告警组列表，包括计数、时间线、通知次数和当前状态。

### 7.3 确认告警

```http
POST /v1/alerts/{id}/ack
```

将告警状态变更为 `acknowledged`，记录操作来源。

### 7.4 恢复告警

```http
POST /v1/alerts/{id}/resolve
```

人工将告警变更为 `resolved`。自动恢复由后台 Worker 完成。

### 7.5 运行状态

- `GET /healthz`：检查存储是否可用。
- `GET /metrics`：返回事件数、归并数、通知数和错误数等指标。

## 8. 错误处理与一致性

- 请求格式错误返回 `400`。
- 不支持的 HTTP 方法返回 `405`。
- 资源不存在返回 `404`。
- 持久化失败返回 `500`，同时增加错误指标。
- 事件先落盘，再由 Worker 处理，避免 API 请求期间执行复杂业务逻辑。
- Store 内部使用读写锁，保证并发查询和更新安全。
- 通知失败不会丢失告警计数，通知记录会保存错误信息，便于重试或审计。

## 9. 测试方案

测试覆盖以下内容：

- 消息归一化和敏感信息脱敏。
- 相似度计算和阈值判断。
- JSON 文件数据库写入、重新加载和快照恢复。
- 告警首次创建和重复事件计数。
- 通知首次触发和重复抑制。
- HTTP API 请求校验和返回结构。
- 后台 Worker 的事件处理和恢复扫描。

测试使用临时目录数据库，不依赖外部网络、消息队列或第三方通知服务。

## 10. 运行校验

```bash
go test ./...
go vet ./...
go run ./cmd/aggregator -addr :8080 -db ./data/alerts.json
```

提交前检查非测试代码规模：

```bash
find . -name '*.go' ! -name '*_test.go' -print0 | xargs -0 awk 'END{print NR}'
find . -name '*.go' ! -name '*_test.go' | wc -l
```

项目约束：

- 非测试 Go 代码行数大于 2000 且小于 2200。
- 非测试 Go 文件数大于 20 且小于 25。
- 当前实现包含数据库、迁移、API、后台归并、测试和运行验证。
